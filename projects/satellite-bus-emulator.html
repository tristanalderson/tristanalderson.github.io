Project

Satellite Bus Emulator

A from-scratch flight computer platform for the AMD Kria KV260 — custom Yocto Linux running JPL's F Prime flight software, boot to telemetry from source.

Role

Platform architect, embedded Linux engineer

Stack

Yocto, F Prime, Zynq UltraScale+, ARM Cortex-A53

Repo

satellite-bus-emulator

Why I Built This

I wanted to learn what actually sits between "bare silicon" and "spacecraft sends telemetry." Turns out the answer is mostly BitBake errors.

More seriously: I have an AMD Kria KV260 dev board (Zynq UltraScale+ K26 SOM), and I wanted to follow a signal from a physical pin through programmable logic, software, telemetry, and a ground station. Eventually I'd like to design a custom PCB to replace the dev kit, and maybe launch a CubeSat. That's the long-term dream. For now this is where I'm learning.

What It Is

A flight computer stack built entirely from source for the KV260:

  • Custom embedded Linux platform (Yocto, rel-v2024.2)
  • JPL's F Prime flight software framework running on ARM Cortex-A53
  • Telemetry and commanding over TCP to a ground station (fprime-gds)
  • Boot chain: factory QSPI firmware hands off to SD card image (kernel + device tree + rootfs)

The flight side connects as a TCP client — same operational model as real spacecraft. The ground station must be listening first.

Key Engineering Decisions

Yocto SDK Approach

Cross-compilation uses the Yocto-generated SDK instead of a distro cross-compiler, so the toolchain and target rootfs share the same libc by construction. That one decision quietly eliminates the whole "works on my toolchain, segfaults on the board" class of bug.

Factory QSPI Preservation

The 2024.2 setup uses the KV260's factory boot firmware (FSBL/PMU/ATF/U-Boot) before loading the SD image. I could have built my own copies from source — Yocto produces them — but there's nothing to gain and a bricked SOM to lose. Firmware compatibility depends on versions; I kept a recovery path.

Why F Prime

F Prime is NASA's flight software framework, component-driven and designed for spacecraft. I wanted to understand how real missions structure their command and data handling. The topology is generic right now (comm stack, command dispatcher, events, telemetry channels, rate groups) but that's the starting point for adding custom components later.

Current State

The 2024.2 platform boots, runs the F Prime deployment, and exchanges telemetry/commands with the ground station over TCP. That's the baseline. Deployment verified (July 2026)

I'm currently migrating from the hand-assembled 2024.2 Yocto config to AMD's EDF (Embedded Development Flow) — a reproducible, manifest-driven release that replaces bespoke layer assembly with vendor-maintained provenance. The migration plan is written, the scaffolding scripts are in place, but I haven't tested on hardware yet. EDF migration branch

What I'm Learning

This is a learning-in-public project. I documented my goals in the repo:

  • Follow a signal from physical pin through PL → software → telemetry → ground station
  • Design and verify RTL, understand timing and clock boundaries
  • Explore the division of work between Linux (A53), real-time software (R5), and FPGA logic
  • Learn where hardware work still needs human judgment versus what AI can help with

Possible Next Experiments

These are ideas, not commitments. The order and scope will change as I learn more:

  1. Keep a reproducible platform that boots and exchanges F Prime commands and telemetry
  2. Add a small timestamped event-capture peripheral, simulate its failure cases, and expose measurements to F Prime
  3. Emulate a satellite subsystem with realistic timing, faults, and observable responses
  4. Try a bounded R5 task and measure how it behaves when Linux is busy or restarted
  5. Design a custom K26 carrier with accessible debug, power measurement, and the interfaces the experiments actually need

Working Principles

I wrote down how I want to work on this project — partly for my own clarity, partly because I'm using AI agents to help with certain tasks and wanted to be explicit about boundaries. From the repo's AGENTS.md:

"Check important behavior against evidence independent of the implementation where practical. Distinguish simulation, source review, successful builds, and measurements on hardware; never present one as proof of another."
"Prefer small, useful changes. Do not add infrastructure or process without a concrete need. Keep the approach flexible as the project and the owner's interests change."

That's how I'm trying to work: deliberate about what I'm learning, clear about what's verified versus what's assumed, and willing to change direction as I understand more.

EDF Migration Status

The migration plan defines four gates and a reproducibility milestone:

  • G0: Baseline + host verified ✅
  • G1: Pinned bootstrap parses and replays (in progress)
  • G2: Source-built image + matching SDK with recorded provenance
  • G3: Hardware-verified: three cold boots on KV260, app connects to GDS, commands produce expected responses

Gate 3 is the real test. "It builds" is categorically weaker evidence than "it boots on the board."
