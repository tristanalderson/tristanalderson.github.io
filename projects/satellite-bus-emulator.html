Project

First CubeSat Platform

The flight computer for a CubeSat I'd like to fly someday. For now it lives on a Kria KV260 dev kit: custom Yocto Linux running JPL's F Prime, built from source.

Role

Solo project

Stack

Yocto, F Prime, Zynq UltraScale+, Embedded Linux

Repo

satellite-bus-emulator

The Problem

I wanted to know what actually sits between "bare silicon" and "spacecraft sends telemetry." Turns out the answer is mostly BitBake errors. I have a KV260, and I wanted to pick up where I left off: follow a signal from a physical pin, through programmable logic and software, all the way to a ground station.

What I built

A flight computer stack for the KV260, built from source. A custom Yocto image (rel-v2024.2) boots off the SD card, and an F Prime deployment on the Cortex-A53s sends telemetry and takes commands over TCP from fprime-gds. The flight side is the TCP client, so the ground has to be listening before the spacecraft dials in - same as real life.

Cross-compilation uses the Yocto-generated SDK instead of a distro cross-compiler, so the toolchain and the target rootfs share the same libc by construction. That one decision quietly eliminates the whole "works on my toolchain, segfaults on the board" class of bug.

The layer list looks excessive for "just boot Linux." It isn't - the k26-smk-kv-sdt machine hard-requires the SDT firmware flow, which drags in meta-openamp, meta-virtualization, and friends. Each layer is there because the build broke without it. Verified on hardware (July 2026)

What's next

Right now it's Linux only - the R5 cores and the FPGA fabric sit idle. First I'm moving the platform from my hand-assembled 2024.2 config to AMD's EDF release, so the build is reproducible from a manifest. The plan and scripts are on the edf-migration branch; the image hasn't been tested on the board yet. After that, the experiments I want to try:

  • A small timestamped event-capture peripheral in the PL, with its failure cases simulated and its measurements exposed to F Prime.
  • A bounded task on the R5, measured while Linux is busy or restarting.
  • A Raspberry Pi camera.
  • A custom K26 carrier board with accessible debug and power measurement.

Technical Stack

  • Hardware: AMD Kria KV260 (K26 SOM)
  • Boot: factory QSPI firmware, then kernel, device tree, and rootfs from SD
  • OS: custom Yocto Linux, rel-v2024.2
  • Flight software: F Prime v4.2.x
  • Toolchain: Yocto-generated SDK
  • Ground: fprime-gds over TCP

Timeline

  • Jul 2026: first boot to telemetry, verified on hardware
  • Nov 2026: started the EDF migration
